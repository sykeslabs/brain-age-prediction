# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Predict a person's age from 832 numeric features per subject. The provided features contain irrelevant/redundant columns, outliers, and missing values (NaN) — the pipeline must explicitly handle each of these before regression.

**Data characteristics worth knowing before changing the pipeline** (measured directly on `X_train.csv`/`y_train.csv`): `y` is close to symmetric (skew ≈ -0.2, 56 unique values) — a target transform (log/Box-Cox) is unlikely to help. Feature-to-target correlation is weak and diffuse: max |corr(feature, y)| is only 0.44, none exceed 0.5, and just 49/832 features (5.9%) exceed |corr|>0.3 — this is a genuinely hard, diffuse-signal problem, not one with a hidden strong predictor being missed (and that "~49 real features" count lines up closely with Boruta's unanimous-threshold feature count of 35-50, a good consistency check that feature selection is finding roughly the right things). Average pairwise feature correlation is also low (0.049), and PCA only captures 32% of variance in the top 50 components — features are close to mutually uninformative, which is why cross-feature-aware imputation (`KNNImputer`) measured *worse* than plain per-column median (0.4537±0.0210 vs 0.4656±0.0688 nested CV R²) and why a PCA-based feature representation wasn't pursued further.

## Commands

- Run the full pipeline: `python main.py`
- Run tests: `python -m pytest`
- No linter is configured yet.
- `regression.py` depends on `catboost` (`pip install catboost`) in addition to the usual numpy/pandas/scikit-learn stack — one of the regression candidate families.

## Testing

Always use pytest for tests. Each pipeline module (`impute.py`, `outliers.py`, `feature_selection.py`, `scale.py`, `regression.py`) gets a matching `test_*.py` file. Run `python -m pytest` at the end of every change, before considering it done.

## Data files

- `X_train.csv` — 1212 rows, columns `id, x0..x831` (832 numeric features, contains NaNs and outlier rows).
- `y_train.csv` — 1212 rows, columns `id, y`. Target `y` is age, observed range roughly 50–90.
- `X_test.csv` — 776 rows, same `id, x0..x831` schema as `X_train.csv`. No target provided.
- `sample.csv` — 776 rows, columns `id, y`, the expected submission format.

Row order in `X_train.csv` matches `y_train.csv` (`id` is a 0-based row index in both); `X_test.csv` row order matches the expected submission order.

**Do not modify `X_train.csv`, `y_train.csv`, `X_test.csv`, or `sample.csv`.** These are the original input files — all cleaning/transformation happens in-memory or on copies; never overwrite them in place.

## Pipeline architecture

`main.py` is the entry point and orchestrates the pipeline as sequential stages, each in its own module:

0. **`split.py`** — Split the provided training data into train/validation (`val_size=0.1`, `random_state=42`) before any other stage runs. Validation is never used to pick a model or hyperparameters (see stage 6) — only to compute an honest post-hoc diagnostic and, once selection is already locked in, to help fit the model actually deployed (see "Final refit" under stage 6). `val_size=0.1`, not the more conventional 0.2: sensitivity-checked via nested CV — more rows left in the training fold directly means larger CV folds inside `select_best_model`, which measurably tightened the selection signal for a fixed RandomForest config (cv std dropped ~46%, 0.0688→0.0372, mean also rose 0.4656→0.4896) at no cost to the deployed model, since the final refit uses train+validation combined regardless of this ratio. (Caveat: this gain didn't compose as cleanly as hoped once combined with the `k=2.5` change below and the full 31-candidate grid — that same RandomForest config's std actually rose slightly in the full pipeline, 0.0750 vs the isolated 0.0372 — so treat the individual-lever numbers above as directional, not as guaranteed to add up; the combined configuration's own end-to-end CV score is what's tracked in stage 6.)
1. **`outliers.py: remove_cell_outliers`** — Corrects extreme *individual cell* values (a handful of (row, feature) values replaced with implausible numbers, scattered across many different rows) as distinct from whole anomalous *rows* (stage 3). Runs BEFORE imputation, on train/val/**test alike** (unlike row-level removal below, which is train-only) — per-column IQR bounds (`k=2.5`) are fit on the training fold only, then any value outside those bounds in any split becomes NaN, to be filled by the same imputer as any other missing value. `k=2.5`, not the more conventional 3.0: sensitivity-checked via nested CV across 2.0-4.0 with a fixed model — 2.5 gave both a higher mean R² and a notably tighter std (0.0463 vs 0.0688 at k=3.0), i.e. tighter bounds catch more real corruption without over-flagging legitimate values. Added because a single corrupted cell among hundreds of features barely shifts a row's overall multivariate anomaly score, so `IsolationForest` (stage 3) is nearly blind to this failure mode — and because row-level removal never touched validation/test at all, cell-level correction was the first thing in the whole pipeline that actually corrects test-set feature values before predicting on them.
2. **`impute.py`** — Fill missing values (NaNs) — both the originally-provided ones and any newly flagged by stage 1. Fits imputation statistics on the train fold only; transforms validation and test with those same statistics.
3. **`outliers.py: remove_outliers`** — Detect and remove whole outlier *rows* from the training fold only (never from validation or test — every one of their rows must get a prediction/score). Operates after imputation. `contamination="auto"` (removes ~4 of 969 rows) was sensitivity-checked against 0.01/0.02/0.05/0.1 via downstream CV R² — 0.02 is statistically tied (0.492 vs 0.492, within a ~0.07 std), higher values consistently score worse and less stably. Current default is already near-optimal, not an oversight.
4. **`feature_selection.py`** — Two stages: (a) prune redundant features via pairwise correlation (drop near-duplicates above `correlation_threshold`), processed in **descending order of `|correlation with y|`, not raw column order** — when two features are near-duplicates, the one more relevant to the target is kept, not whichever happened to appear earlier in the CSV (a plain column-order greedy pass could otherwise discard the *better* of two correlated informative features purely by accident of column position); (b) keep the top `k=100` post-redundancy features by univariate F-test score (`SelectKBest(f_regression)`).

   **This replaced a Boruta-style shadow-feature test** (compare each feature's Random Forest importance against a shuffled copy of itself over several trials, keep only features that beat the best shadow feature in at least `confirmation_threshold` of them) that was the original design and is where the `confirmation_threshold=1.0`-vs-0.5 tuning story documented in earlier revisions of this file lived — unanimous voting beat majority voting beat no selection at all (≈0.49 vs ≈0.48 vs ≈0.41 nested CV R², all under Boruta). That comparison is now moot: once SVR became the strongest model family (see stage 6), a direct nested-CV comparison of Boruta vs. the F-test filter against SVR specifically — re-run across 3 independent CV fold partitions (seeds 42/1/7) to rule out a lucky split — found the F-test filter beating Boruta by a large, consistent margin on every single seed (0.5098/0.4875/0.4896 for Boruta vs. 0.5290/0.5285/0.5147 for the F-test filter at k=100, a +0.02 to +0.04 R² swing each time, never in Boruta's favor). The likely reason: Boruta's RandomForest-importance criterion rewards whatever a tree ensemble finds useful, including features that only pay off through splits/interactions, while SVR's RBF kernel instead rewards features with a clean univariate relationship to the target — exactly what `f_regression` measures directly. `k=100` was the consistent best (or tied-best) of `{75, 100, 125, 150}` across all 3 seeds. Mutual-information-based filtering (`mutual_info_regression`) was also tried as a univariate alternative and was consistently *worse* than both Boruta and the F-test filter (~0.45-0.49 across `k`) — its extra flexibility to detect non-linear relationships isn't earning its keep here, most likely because it also has higher variance as an estimator on this few-hundred-row-per-fold data, actively hurting a filter step. A Lasso-coefficients-as-selector approach (keep whichever features get non-zero weight from a fitted `Lasso`) was tried too and also came in below both alternatives (≈0.43-0.46, peaking at `alpha=1.0` keeping ~16 features) — Lasso's selection criterion is itself a linear-model artifact (which coefficients a *penalized linear fit* zeroes out), one step more removed from "does this feature correlate with y" than `f_regression` measures directly.
5. **`scale.py`** — Scale the selected features with `QuantileTransformer(output_distribution="normal")` (rank-based, not `RobustScaler`'s median/IQR or `StandardScaler`'s mean/std). Earlier stages (Isolation Forest, Random Forest, Pearson correlation) are all scale-invariant so this couldn't have been done earlier for free, but it matters once regression starts — specifically for SVR and Ridge; tree-based candidates are invariant to any monotonic per-feature transform, so the scaler choice only ever changes those two families' scores. `QuantileTransformer` over `RobustScaler`: once SVR became the strongest model family (see stage 6), a direct nested-CV comparison against SVR specifically found `QuantileTransformer` ahead by a real, non-marginal margin across a broad `C`/`epsilon` plateau — 0.5104±0.0664 vs `RobustScaler`'s 0.4992±0.0661 at the same `SVR(C=15, epsilon=3.0)` config — and re-tuning `C`/`epsilon` under `QuantileTransformer` from scratch landed on that same config as its own peak, confirming the gain isn't an artifact of hyperparameters chosen for a different scaler. `n_quantiles` is capped at the training fold size (sklearn's default of 1000 exceeds every fold here, ~860-1200 rows, and would otherwise auto-clip with a warning on every single CV fold of every pipeline run).
6. **`regression.py`** — `select_best_model(X_train, y_train, X_val, X_test, y_val, candidates=None, random_state=42, cv_folds=5, feature_selector=select_features, scaler=scale_features, enable_stacking=True, refit_on_combined=True)` fits ~38 candidate models (Ridge, RandomForest, HistGradientBoosting, CatBoost, SVR, GPR, each with several hyperparameter settings — GPR gets just one, see below). `cv_folds` is configurable — raising it to 10 was tried and measured statistically indistinguishable from 5 (differences well inside the ~0.09-0.10 per-fold std), so it's not a settled lever either way; `main.py` currently runs at 5 for faster iteration while the candidate grid is still being tuned. Selection is by **mean CV R² on the training fold only** — `X_val` is never used to pick the winner (with only ~243 validation rows, comparing candidates against one fixed split picks whichever fits that split's noise best, not whichever generalizes best — observed swing across random splits: R² 0.42–0.54). `val_r2` is still computed and displayed per candidate as a diagnostic, never as the selection criterion.

   **Several extensions were tried here and reverted; all are documented in `regression.py` rather than repeated here in detail.** (a) `StratifiedKFold` on age deciles instead of plain `KFold(shuffle=True)` — measured *worse*: CV mean dropped and CV std roughly doubled across nearly every candidate, because per-fold difficulty on this dataset is driven by individual subjects' feature-space idiosyncrasies, not by their age, and stratifying by age doesn't address that. (b) A `max_samples` axis on RandomForest plus a stochastic-gradient-boosting (`subsample<1.0`) candidate family — measured *neutral* (within CV noise) for the stacked ensemble's score, at the cost of 17 extra candidates × 5 Boruta folds of runtime. (c) `ElasticNet` and `ExtraTrees` candidate families — both measured as strictly redundant with what's already here: ElasticNet tracked Ridge's already-weak ~0.32-0.34 linear ceiling almost exactly, and ExtraTrees tracked RandomForest but always slightly worse on every matching config. (d) `XGBoost` — removed for an architectural reason, not just a bad hyperparameter draw: its sklearn API needs an explicit `eval_set` to early-stop, which the shared fold loop doesn't provide (unlike `HistGradientBoostingRegressor`, which splits its own internal validation set automatically), so it overfit badly at any real depth (train R²=1.0, cv dropped to ~0.38-0.39) — and even its best, shallowest config still scored below HistGradientBoosting's best. All four removed; none were oversights.

   **Feature selection and scaling are called from inside this function** — once per CV fold (shared across all candidates within that fold) and once more on the full training fold to produce the final deployed model — rather than once upfront in `main.py` like `impute`/`outliers` are. Both use `y_train`, so fitting them once outside the fold loop leaks each fold's held-out rows' influence into the feature set it's later scored on. Measured impact on this dataset: ~0.014 R² of false optimism (leaky global-selection estimate 0.500 vs. honest nested estimate 0.486, same model/threshold). `feature_selector`/`scaler` are injectable specifically so tests can substitute a cheap no-op instead of re-running Boruta for every fold. A separate sweep of Boruta's `confirmation_threshold` in the 0.5–1.0 range (motivated by the note below) found no reliable win either — differences across thresholds were smaller than fold-to-fold noise when measured against the full candidate/stacking pipeline, so the unanimous default (1.0) stands.

   `RandomForestRegressor` needs `max_features="sqrt"` (same regularization gap as the Boruta stage) and `HistGradientBoostingRegressor` needs `early_stopping=True` explicit (its `"auto"` default silently resolves to `False` below 10,000 samples) — without these, train R² balloons to 0.93–0.98 while validation R² doesn't move, i.e. wasted model capacity, not real predictive power. `CatBoostRegressor` runs with `verbose=False, allow_writing_files=False` (silences per-iteration logging and stray artifact files across hundreds of fold×candidate fits) and no early stopping (same eval_set gap as XGBoost, but its depth/l2_leaf_reg grid alone was already competitive — best val_r2 of any single candidate — so it wasn't worth chasing further). **Selection is a strict three-way split** (train fits each fold, CV-on-train picks the model/hyperparameters, validation contributes nothing to that choice) — but note the final refit below.

   **`SVR` (RBF kernel)** was added as a fifth family after Ridge/RandomForest/HistGradientBoosting/CatBoost all turned out to be either linear or tree-based — a kernel method gives the stack a genuinely different error pattern to blend, not just another hyperparameter variant of what's already there. `gamma="scale"` is fixed (measured consistently better than `"auto"` at every competitive `C`); the `C`/`epsilon` grid is centered on a measured peak from a nested-CV sweep on Boruta-selected features: `C=15, epsilon=3.0` scored 0.4992±0.0661, beating every RandomForest/HistGradientBoosting/CatBoost candidate at the time this was measured. `epsilon` was swept past 3.0 up to 8.0 and the score strictly declined, confirming this is a real peak rather than a grid-edge artifact. No `eval_set`/early-stopping gap here (unlike XGBoost) — `SVR.fit` needs nothing beyond what the shared fold loop already provides, so it slots in exactly like Ridge or RandomForest.

   **`GaussianProcessRegressor` (RBF + white-noise kernel)** was added as a sixth family — still RBF-kernel-based like SVR, but fitting its length-scale and noise level from data via marginal-likelihood optimization instead of grid search, and giving a genuinely different fit procedure for the stack to diversify against. Kernel: `ConstantKernel(1.0) * RBF(length_scale=10.0) + WhiteKernel(noise_level=1.0)`, `normalize_y=True`, `n_restarts_optimizer=2`. Compared head-to-head against production `SVR(C=15, epsilon=2.0)` via nested CV across 3 independent fold-seed partitions (42/1/7) to rule out a lucky split: GPR won every single seed by a modest but consistent margin (0.5367/0.5339/0.5201 vs SVR's 0.5332/0.5273/0.5182). Kept to a single config (unlike SVR's 6) — and this isn't just a cost-driven choice: a `{5.0, 10.0, 20.0} length_scale × {0.5, 1.0, 2.0} noise_level` sweep of initial values scored *identically* (0.5367±0.0940) on every combination, because `GaussianProcessRegressor` re-optimizes these hyperparameters itself via log-marginal-likelihood during `fit()` — unlike SVR's `C`/`epsilon`, they aren't a tunable grid here, just an optimizer starting point that washes out.

   **Stacking (`enable_stacking=True` by default)**: after the fold loop, one "champion" per model family (best Ridge, best RandomForest, best HistGradientBoosting, best CatBoost, best SVR, best GPR, picked by their own CV mean) is blended by a `LinearRegression(positive=True)` meta-learner and added to `results` as one extra `"Stacked(Ridge+RandomForest+HistGradientBoosting+CatBoost+SVR+GPR)"` candidate — `max(results, key=cv_r2_mean)` then picks it automatically if, and only if, it actually wins. Chosen over stacking all ~38 candidates because most within a family are near-duplicates (same model, different hyperparameters) and would just feed the meta-learner redundant, correlated inputs instead of the diverse, low-correlation error patterns stacking is meant to exploit. The stack's own CV score is computed honestly on the *same* fold boundaries as every other candidate: each fold's out-of-fold predictions (already produced by the main fold loop, previously discarded after computing `fold_scores`) are reused to train/score a meta-learner per outer fold, so a row's stacked prediction is never influenced by a base model that saw that row. The meta-learner is deliberately a small non-negative-weight linear blend (now 6 inputs), not another complex model — stacking is known to overfit quickly on datasets this small (~969 training rows), so meta-learner capacity is kept minimal on purpose. If there's only one family among the supplied `candidates` (e.g. in tests), stacking is skipped — nothing to diversify across. Note that adding CatBoost narrowed the stack's edge over the best single model to within noise (plain RandomForest has occasionally out-scored the stack by CV since) — stacking is no longer a clear, reliable win on its own, just historically the best-performing single candidate slot more often than not.

   **Selection rule is argmax-on-cv_r2_mean, with one exception**: if the stacked ensemble is statistically indistinguishable from the raw winner — its mean is within one standard error of the *paired per-fold difference* between the two (same fold boundaries for both, so this is a more powerful/less noisy test than comparing their two independent `cv_r2_std` values) — the stack is deployed instead. This is the "1-SE rule" from CART pruning / lasso lambda selection (Hastie/Tibshirani/Friedman, *ESL*) applied to model choice: among candidates tied within noise, prefer the more robust one, since a blend is inherently lower-variance than any single base learner it's built from. This isn't a theoretical concern — it fixed a real, observed failure: two Kaggle submissions differing only in `cv_folds` (10 vs 5) had their raw-argmax winner flip between the stack and a plain RandomForest that beat it by just 0.0006-0.0015 locally, and the leaderboard score dropped (0.6344→0.6174) when the flip landed on the single model. The rule is still purely a function of `X_train`'s own CV folds — it never looks at validation or leaderboard feedback, so it doesn't compromise the honesty of selection, just its stability.

   **Final refit (`refit_on_combined=True` by default)**: once `best` is chosen by CV (using only `X_train` — this step never influences selection), its exact winning configuration is refit on train+validation **combined** before it generates any prediction — standard Kaggle practice: selection must never see validation, but the model that actually produces `submission.csv` should use every labeled row available, not leave ~20% of it on the table. `cv_r2_mean`/`val_r2`/`train_r2` on `best` are computed *before* this refit and are left untouched — they remain honest diagnostics of the train-only fit that was used to pick the model, not a description of what `best["model"]` now actually is. For the stacked ensemble, only the base-model champions are refit on the combined data; the meta-learner's blend weights are **not** refit — they stay as learned from the honest out-of-fold matrix over `X_train`'s own CV folds, the same asymmetry already used when going from fold-level to full-training-fold fits. Set `refit_on_combined=False` to keep the model actually fit on train-only (e.g. for a test that wants to isolate this behavior).

`main.py` wires these stages together in order (split → cell-level outlier correction → impute → remove outlier rows → select best model, which internally does feature selection + scaling + regression + the final combined-data refit), prints every candidate's CV mean±std / train / validation R² with the selected one marked, and writes `submission.csv` in the `sample.csv` format (columns `id, y`).

Keep each stage's fit/transform split explicit: statistics or selectors learned from the training fold must be reused (not refit) when transforming validation or test data.

## Evaluation

`X_test.csv` has no labels — there is no way to compute a real test score locally. The validation R² printed by `main.py` is the only local signal; the actual score only appears on Kaggle's leaderboard after uploading `submission.csv`. Target: validation R² ≥ 0.5.
